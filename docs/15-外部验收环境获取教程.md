## 开始前：怎么打开命令窗口，怎么复制命令

1. 按键盘上的 **Win 键**，输入 `PowerShell`。
2. 普通命令直接点击打开；只有教程明确写“管理员”时，才右键选择“以管理员身份运行”。
3. 复制灰色代码框里的内容，粘贴到窗口，按 **Enter（回车）**。
4. 一次执行一条。出现结果后，再执行下一条。

代码框外的说明文字、三个反引号和窗口里的 `PS C:\...>` 提示符，都不用复制。

按 **Win + E** 可以打开文件资源管理器。在顶部地址栏粘贴文件夹路径，按回车，就能进入对应文件夹。

## 第 1 步：让电脑能够运行 Docker

Docker 可以理解成“帮你运行数据库等项目组件的工具”。本步骤只检查工具，不需要你自己配置数据库。

### 1.1 已经安装过 Docker 的人，先这样做

1. 按 Win 键，搜索 `Docker Desktop`。
2. 能找到就打开，等待它启动完成。第一次打开可能需要接受使用条款。
3. 不确定是否已经启动成功，没关系，直接跳到 **1.4** 用命令检查。

如果搜索不到 Docker Desktop，再从 1.2 开始安装。

### 1.2 安装 Docker 需要的 WSL

WSL 是 Windows 运行 Linux 环境的组件。你不用为了这一步学习 Linux。

先打开普通 PowerShell，执行：

```powershell
wsl --version
```

**如果已经显示 WSL、内核等版本信息：** 说明已经安装，先去 1.3。若 Docker 后面提示 WSL 太旧，再用管理员 PowerShell 执行 `wsl --update`，按提示重启。

**如果明确提示没有安装：** 用管理员身份打开 PowerShell，执行：

```powershell
wsl --install
```

等命令完成后，**重启电脑**。首次打开随之安装的 Ubuntu 时，若要求创建用户名和密码，按窗口提示设置。输入 Linux 密码时屏幕不显示字符，这是正常现象。

如果只出现帮助文字、下载卡住或报错，先把输出发给代理判断，不要反复安装。已经有 WSL 时，也不必重复创建 Ubuntu。

说明来源：[Microsoft 的 WSL 安装教程](https://learn.microsoft.com/windows/wsl/install)。

### 1.3 安装 Docker Desktop

1. 浏览器打开 [Docker 官方 Windows 安装页面](https://docs.docker.com/desktop/setup/install/windows-install/)。
2. 点击 Windows 的下载按钮。普通 Intel/AMD 电脑选 **x86_64 / AMD64**；只有 Windows 设置里明确写 ARM 处理器时才选 Arm。
3. 下载完成后，打开安装文件，按默认引导安装。出现后端选择时使用 **WSL 2**。
4. 安装器要求重启或退出登录时，按它的提示操作。
5. 从开始菜单打开 Docker Desktop，等待启动完成。若能跳过账号登录，可以先跳过。

如果提示虚拟化未启用，按 **Ctrl + Shift + Esc → 性能 → CPU** 查看“虚拟化”。显示“已禁用”时，把电脑型号和提示发给代理或机房管理员，再按对应机型处理。

### 1.4 检查是否真的能运行

新开一个普通 PowerShell，依次执行下面三条命令：

```powershell
docker version
```

```powershell
docker info --format '{{.OSType}}'
```

```powershell
docker compose version
```

**看到下面三项，就完成了本步骤：**

- 第一条的结果中同时有 `Client` 和 `Server`。
- 第二条返回 `linux`。
- 第三条显示 Docker Compose 的版本号。

只看到 Client、看不到 Server，通常是 Docker 引擎还没起来，不能算完成。

| 你看到的情况 | 下一步怎么做 |
|---|---|
| 提示找不到 `docker` 命令 | 先关闭 PowerShell，再重新打开；仍找不到就检查 Docker 是否安装完成 |
| 出现 `docker_engine`、`pipe`、`Cannot connect` 等连接错误 | 打开 Docker Desktop，等启动完成后重试 |
| 第二条显示 `windows` | 在 Docker 托盘图标菜单中寻找切换到 Linux containers 的选项；找不到就发菜单截图给代理 |
| Docker 提示 WSL 版本过旧 | 管理员 PowerShell 执行 `wsl --update`，按提示重启 |
| 一直启动失败 | 发 Docker 错误提示和上面三条命令的输出；先不要恢复出厂设置 |

**现在要保存的东西：** 这三条命令的输出。直接复制文字即可。

## 第 2 步：把项目放到你自己的 GitHub 仓库

GitHub 用来保存代码，并自动运行检查。GitHub Desktop 是它的桌面工具，用按钮操作，比手写 Git 命令容易。

### 2.1 准备账号和桌面工具

1. 打开 [GitHub](https://github.com/)，已有账号就登录；没有就点击注册，按页面完成邮箱验证。
2. 打开 [GitHub Desktop 官方页面](https://desktop.github.com/)，下载并安装 Windows 版本。
3. 打开 GitHub Desktop，点击 `Sign in to GitHub.com`，在浏览器完成登录授权，再回到桌面工具。

如果登录入口没出现，可以在 `File → Options → Accounts` 中找。

### 2.2 选择已经存在的项目

1. GitHub Desktop 顶部点击 **File → Add local repository**。
2. 点击 **Choose**，选择这个文件夹：

```text
C:\Users\123\Desktop\temp\project
```

3. 点击 **Add repository**。
4. 确认选中的是整个 `project`，不是 `docs`、`backend` 或 `frontend` 子文件夹。

本次改写时，该目录已经有 Git 仓库。不要另建一个空项目替代它。如果工具说这里不是仓库，先核对文件夹路径，再把提示发给代理。

官方操作参考：[将本地仓库加入 GitHub Desktop](https://docs.github.com/en/desktop/adding-and-cloning-repositories/adding-a-repository-from-your-local-computer-to-github-desktop)。

### 2.3 上传前，先让当前改动整理好

在左边的 `Changes` 中看到很多文件，不等于出错，可能是代理还在开发。本项目目前确实存在尚未提交的改动。

先把这段发给负责实现的代理：

> 我要使用 GitHub Desktop 上传现有项目。请先完成并核对当前这轮改动，检查待提交文件和已有 Git 历史是否含真实密码、私钥、令牌、运行数据或缓存。告诉我哪些文件可以提交。只做本地检查和整理，上传由我在 GitHub Desktop 完成。

代理确认好以后，你再做：

1. 在 `Changes` 中勾选代理确认可以提交的文件。
2. 在左下角 `Summary` 填一行说明，例如“准备课程验收版本”。
3. 点击 **Commit to main**；按钮中的分支名以你当前实际分支为准。

如果已经没有待提交改动，可以直接继续。不要点击 `Discard changes`，它会丢弃尚未提交的修改。

### 2.4 发布到 GitHub

如果顶部显示 **Publish repository**：

1. 点击它。
2. `Name` 填 `yueji-bookstore`，也可以用自己喜欢的项目英文名。
3. **保留勾选 `Keep this code private`**，先作为私有仓库保存。
4. 个人项目的 `Organization` 选择 `None`；团队项目按约定选择组织。
5. 点击 **Publish repository**，等上传完成。

如果显示的是 **Push origin**，说明已经关联了远端仓库：先确认那是你自己的目标仓库，再点击推送，不要重复新建仓库。

上传后，在菜单 **Repository → View on GitHub** 打开网页。能看到 `backend`、`frontend`、`docs` 等目录，就说明代码上传了。复制浏览器地址栏中的仓库链接，保存下来。

官方操作参考：[用 GitHub Desktop 发布已有项目](https://docs.github.com/en/desktop/adding-and-cloning-repositories/adding-an-existing-project-to-github-using-github-desktop)。

### 2.5 查看自动检查

1. 在仓库网页上点击 **Actions**。
2. 若页面要求确认启用已有工作流，阅读提示后启用。
3. 找到名为 `quality-release` 的运行记录并打开。
4. 黄色表示在运行，绿色表示这次流程成功，红色表示某一步失败。

红色时，点击失败的任务，再展开红色步骤，把错误文字和这次运行的网页链接发给代理。代码测试失败、账号权限不足、下载失败是不同问题，让代理判断即可。

如果提示私有仓库不能使用 CodeQL 或 Environments，把原文发给代理，**先保留私有状态，不必为了继续操作直接改成公开或购买套餐**。这些功能确实受仓库类型和账号权限影响，当前项目已有扫描工作流，也不必再点 GitHub 的按钮生成第二套 CodeQL 配置。参考 [CodeQL 可用范围](https://docs.github.com/en/code-security/concepts/code-scanning/codeql/codeql-code-scanning)和 [Environments 可用范围](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments)。

本项目的镜像上传使用工作流自带的短期 `GITHUB_TOKEN`。你现在不用额外创建 `GHCR_TOKEN`，也不用把密码交给 PR。说明见 [GitHub 官方镜像仓库文档](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry)。

**现在要保存的东西：** 仓库链接、私有/公开状态、Actions 运行链接；失败时再附错误文字。

## 第 3 步：准备支付宝沙箱

沙箱可以理解成“支付宝提供的练习环境”。你登录开放平台可以使用本人的账号，但后面测试付款使用的是**沙箱虚拟买家和虚拟余额**。

商家出款继续使用项目里的模拟方式，不需要你开通真实银行出款或转账服务。

### 3.1 进入沙箱，找到应用和账号

1. 打开 [支付宝沙箱入口](https://open.alipay.com/develop/sandbox/app)。若跳到登录页，先由本人登录。
2. 直接入口打不开时，从 [支付宝开放平台](https://open.alipay.com/)进入控制台，查找“沙箱”或“沙箱环境”。
3. 页面中有现成沙箱应用就使用该应用；先确认页面写着“沙箱”。找不到时发一张遮住账号隐私的页面截图给代理定位，不必去申请生产支付产品。
4. 找到 `APPID` 或 `应用 ID`，复制到你本机的准备记录里。
5. 找到沙箱账号区域，分别查看**卖家账号**和**买家账号**。
6. 记录卖家的“用户 ID / UID”，后面对应 `ALIPAY_SELLER_ID`。找不到这个字段就保留问题，不要用手机号、邮箱或 APPID 代替。
7. 将虚拟买家的登录方式和密码保管在自己的受限位置；在本机确认可以按平台提供的方式登录，且有可用虚拟余额。发给代理的记录只写“能登录/不能登录”，不用贴密码。

如果平台需要沙箱版支付宝客户端，只从控制台提供的官方入口下载。手机不支持该客户端时，告诉代理手机系统和页面提示，先确认能否使用网页支付方式或借用兼容测试设备。

**这一步完成时，你应当知道：APPID 是什么、卖家 UID 是什么、虚拟买家如何登录。**

### 3.2 先准备一个专门放密钥的文件夹

密钥是一长串字符。公钥可以按要求配置到平台；**应用私钥要留在你的受限文件里**。

先把这段发给代理，让它处理 Windows 文件权限：

> 请在项目目录之外准备 `C:\Users\123\yueji-secrets`，按本机实际用户设置受限访问权限。它将保存支付宝沙箱密钥。请确认目录可用，告诉我怎样保存文件；不要读取或回显目录中已有的密钥，也不要把它加入 Git 仓库。

等代理确认目录权限后，再做下一步。不需要你手动研究 Windows 权限继承。

### 3.3 用官方工具生成应用密钥

下面按**第一次配置这个沙箱应用**说明。若它已经配置了密钥，先告诉代理“已有配置”，不要直接覆盖原来的密钥。

1. 在沙箱应用里找“接口加签方式”“密钥设置”或“RSA2”相关设置。
2. 通过该页面提供的入口下载支付宝官方密钥工具或开发助手。
3. 在工具里选择 **RSA2** 生成密钥。如果工具让你选语言/私钥格式，本项目是 Java，按其说明选择 Java 对应的 **PKCS8** 格式。
4. 工具会产生两份不同的内容：**应用公钥**、**应用私钥**。
5. 把“应用公钥”复制到这个沙箱应用的公钥设置中，保存。
6. 把“应用私钥”保存成下面的文件，内容原样保留，不发到聊天里：

```text
C:\Users\123\yueji-secrets\alipay-app-private-key.txt
```

7. 回到沙箱应用设置，寻找“查看支付宝公钥”，把取得的**支付宝公钥**保存成：

```text
C:\Users\123\yueji-secrets\alipay-public-key.txt
```

用记事本保存时，选择“另存为”，文件类型选“所有文件”，编码选 UTF-8，再确认文件名与上面一致。若工具自带保存功能，也可以用它保存；把实际文件路径告诉代理即可。

支付宝官方说明要求应用公私钥相匹配、使用 RSA2，并区分沙箱与线上公钥。参考 [官方沙箱密钥说明](https://github.com/AlipayDocs/open-docs/blob/main/support/支付宝小程序/常用工具/沙箱环境中如何联调小程序.md)中的“设置接口加签方式”；该页面是小程序资料，这里只引用密钥原则，不代表本商城支付能力已通过测试。控制台内的按钮仍以本人登录后看到的页面为准。

### 3.4 这三个名字怎么分

| 名字 | 你做什么 |
|---|---|
| 应用公钥 | 上传到支付宝沙箱应用设置 |
| 应用私钥 | 保存为 `alipay-app-private-key.txt`，由后端在受限环境读取 |
| 支付宝公钥 | 从支付宝平台取得，保存为 `alipay-public-key.txt`，供后端验签 |

发给代理的是**文件路径**，不是文件内容。如果页面只让你下载证书，或者你看到的字段与这里不同，先发页面字段名称或遮敏截图，让代理确认格式。

**现在要保存的东西：** 沙箱 APPID、卖家 UID、两份密钥文件的实际路径、虚拟买家是否可登录。付款、退款和账单权限是否真的可用，后面由代理实际调用验证。

## 第 4 步：下载临时公网入口工具

本机的商城地址只能在本机或指定网络里访问；支付宝服务器需要一个能从互联网访问的通知地址。这里先下载 `cloudflared`，之后由代理为商城准备好入口再使用。

Cloudflare Quick Tunnel 可提供临时 HTTPS 地址，不要求你先购买域名或注册 Cloudflare 账号。这是测试入口，关闭工具后地址就失效。来源：[Cloudflare Quick Tunnel 说明](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/)。

### 4.1 下载并保存工具

以下步骤按普通 64 位 Intel/AMD Windows 电脑说明；ARM 电脑先让代理确认对应版本。

1. 打开 [cloudflared 官方下载页](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/downloads/)。
2. 按 **Ctrl + F**，搜索 `Windows`，找到 Windows 下载表格。
3. 选择 **64-bit → Executable** 的下载，不用选择 Linux 文件。
4. 按 Win + E，在地址栏输入 `C:\Users\123`，新建文件夹 `yueji-tools`。
5. 把下载的文件移动到这个文件夹，重命名为 `cloudflared.exe`。
6. 在资源管理器开启“文件扩展名”显示，确认文件没有变成 `cloudflared.exe.exe`。Windows 11 通常在“查看 → 显示 → 文件扩展名”。

### 4.2 确认工具能打开

普通 PowerShell 执行：

```powershell
& 'C:\Users\123\yueji-tools\cloudflared.exe' --version
```

看到版本号就可以了。若提示找不到文件，回到文件夹确认保存位置和文件名。

**做到这里先停一下。** 商城需要先启动，入口端口也需要由代理核对。此时不用猜 `5173` 或 `8080`，也不用去修改路由器。

## 第 6 步：需要远端部署时，再准备 Linux 测试服务器

本机跑通商城和“GitHub 自动部署到远端”是两件事。要验证远端发布，需要一台 GitHub 的运行机器能通过 SSH 连接到的 Linux 测试机。

### 6.1 先问学校、老师或团队有没有现成资源

你可以把下面这段发给资源负责人：

> 我有一个课程商城项目，需要一台用于验收的 Linux 测试机。计划使用 Ubuntu 24.04 LTS、Docker 和 Compose；基础配置为 4 vCPU、8GB 内存、80GB SSD。需要专用部署账号、可达的 SSH 入口和 HTTPS 网站入口。监控与正式压测使用独立资源；若只是日常演示并把监控放同机，项目建议 16GB 内存。还需要一个独立备份位置。请先告诉我有哪些现成资源和使用时限，不用先替我开通付费服务。

有资源时，让负责人提供**主机地址、SSH 端口、部署用户名、网站地址、资源规格和可用时间**。账号密码或私钥通过受限方式配置，不贴到聊天里。

没有资源时，告诉代理“没有远端测试机，先保留本地验证和远端未执行记录”。不需要为了填写一张表立即购买服务器。

### 6.2 把服务器安装配置交给代理或管理员

你不用自己配置 Linux 权限和 sudo。把这段交给实施代理，再让主机管理员配合：

> 请按 06、08 和阶段 I 发布清单准备 test 主机，先核对现有数据与权限。项目部署目录使用 `/opt/yueji`，当前部署 wrapper 读取 `/etc/yueji/test.env`。安装受限部署 wrapper、固定命令 sudo 权限、镜像拉取授权、HTTPS 证书、密钥文件及数据目录。只操作授权的 test 环境，说明完成项和剩余项，并给我填写 GitHub Environment secrets 所需的名称及非敏感说明。私钥和密码只通过受限通道注入，不在聊天回显。

你可能听到的 `GHCR` 就是 GitHub 放项目容器镜像的地方。若镜像是私有的，主机还需要只读拉取授权。由账号持有人和管理员按 [GitHub 官方说明](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry)准备 `read:packages` 等必要权限；不要把拉取令牌写进项目代码。

### 6.3 在 GitHub 网页填写 test 环境的五项秘密

**等管理员把服务器准备好，并提供每项实际值以后再做。**

1. 浏览器打开你的项目仓库。
2. 点击 **Settings → Environments → New environment**。
3. 名称填 **test**，点击 **Configure environment**。
4. 找到 **Environment secrets**，点击 **Add environment secret**。
5. `Name` 填下表第一列，`Secret` 填管理员提供的对应内容；每项单独保存。

| Name，必须保持一致 | Secret 填什么 |
|---|---|
| `TEST_DEPLOY_HOST` | GitHub 可以连接到的测试服务器主机名或地址 |
| `TEST_DEPLOY_PORT` | 实际 SSH 端口，只填数字 |
| `TEST_DEPLOY_USER` | 专用部署用户名 |
| `TEST_DEPLOY_SSH_PRIVATE_KEY` | 这一套测试部署专用私钥的完整内容，包括头尾行；公钥由管理员装在服务器 |
| `TEST_DEPLOY_KNOWN_HOSTS` | 管理员通过服务器控制台等可信方式核对指纹后的 known_hosts 内容 |

私钥正文只粘贴到 GitHub 的 Secret 框。Secrets 保存后通常不会再展示原值，属于正常现象；有误时重新设置。

不要把你家电脑的 `localhost` 或 `192.168...` 地址当作 GitHub 已经能连到的服务器地址。没有网络连通方案时，由管理员处理。

如果没有 `Environments` 菜单、无法添加，或提示升级计划，把提示发给代理和项目负责人，先记录权限限制。不要把这些值改放到普通 PR 的配置里。账号支持时，再由代理指导配置 main 分支限制和部署审核。参考 [GitHub 官方环境教程](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments)。

### 6.4 真正运行一次 test 部署

等服务器、备份和配置都就绪，且代理确认代码质量门禁通过以后再做：

1. 和代理确定一个允许测试商城暂时停止服务的时间，这就是“维护窗口”。
2. 在 **Actions → quality-release** 中打开一次 main 分支的成功运行；代理应确认其中生成了可部署的镜像清单。
3. 复制这次运行的网址。网址中 `/actions/runs/` 后面的数字就是运行编号；拿不准就把整个链接发给代理确认。
4. 在 **Actions → deploy-test → Run workflow** 中选择 **main**。
5. `release_run_id` 填刚确认的运行编号。
6. `maintenance_window_id` 填你和代理约定的维护编号；例如 `test-20261026-01` 是格式示例，实际按你的部署日期和批次填写。
7. 点击 **Run workflow**。若出现审核等待，按已设置的流程审核。
8. 等运行结束，让代理核对主机上的发布记录、健康检查、实际冒烟及备份结果，再记录本次部署结论。

看不到 `Run workflow`、没有成功镜像清单或部署失败时，把页面和日志交给代理；不需要自己改 YAML 或跳过失败门禁。本教程只安排 test 部署。

## 第 7 步：准备一个真正独立的备份位置

这一项的目标是：**即使运行商城的电脑或服务器坏了，还能从另一处取回资料。**

### 7.1 你只需要先解决“备份放哪儿”

优先向学校或团队申请另一台机器上的专用备份目录，例如由管理员提供的 SFTP 目录。也可以使用你已经有权限的独立对象存储。

可以这样询问负责人：

> 请提供一个与商城运行主机独立的备份位置，只需要能存取本项目的加密备份。请说明连接方式、主机和端口或存储类型、专用目录、容量和可用期限。账号只给这个备份目录所需权限，访问凭据通过受限方式配置。

同一台电脑的 D 盘、桌面另一个文件夹，只适合练习恢复，不能当作“异地备份”。申请不到时，直接记录“独立备份位置尚未准备”。

### 7.2 其余操作让代理带你完成

取得位置后，把连接方式和非敏感路径交给代理，并发送：

> 请在受限 test 环境准备 age 和 rclone。先做无敏感内容的小文件加密、上传、取回和校验，再按维护窗口执行数据库与文件同批次备份。备份上传前必须加密。随后从独立位置取回，在新隔离库和新文件目录恢复，实际核对数据、文件权限和恢复用时。不要覆盖现有库，也不要把密钥打印到聊天。

这两个工具你只需要这样理解：

- **age**：给备份加密；恢复时需要对应私钥。
- **rclone**：把加密文件上传到备份位置，再取回来。

需要账号登录或存储授权时，由你本人完成。代理应告诉你正在授权哪个目录、需要什么权限。

解密私钥还要单独留一份受限离线副本，例如交给自己保管的加密移动存储；不要只放在运行商城的机器上，也不要和备份一起放到同一个远端目录。

项目要求至少保留 **7 个日备份和 4 个周备份**，由代理核对实际存储策略。你最后应收到真实的“上传、取回、隔离恢复、数据核对”结果，并知道备份中的数据截止到什么时间、恢复花了多久。只有一个压缩包还不能说明恢复成功。

## 第 8 步：安排压测资源和连续 24 小时运行

### 8.1 压测时，你负责提供资源

“压测”是用工具同时发出许多请求，观察商城能否承受。脚本和测试数据由代理准备。

你向机房或老师确认这三项即可：

1. 应用测试机是 **Linux、4 vCPU、8GB 内存、SSD**，用于应用和项目数据库、缓存、消息组件。
2. 发压测请求的机器、监控资源与应用机分开，不在应用机上额外运行它们争抢资源。
3. 能提供足够使用时间，并允许代理记录实际 CPU、内存、磁盘和网络情况。

项目要求的数据量和负载是：10,000 本书、20,000 SKU、100,000 历史订单，预热 5 分钟、正式测 10 分钟，查询 80 RPS 加创建订单 20 RPS。你不用手工造数据，由代理按 01 执行和记录。资源不符合时先写“探索测试”，不要当作正式压测通过。

### 8.2 24 小时测试时，你负责让环境持续可用

如果使用本机：

1. 接通电脑电源，确认网络稳定。
2. 打开 Windows **设置**，搜索“睡眠”。
3. 将“接通电源时，使设备进入睡眠状态”的时间设为“从不”。屏幕可以关闭，电脑不要睡眠。
4. 笔记本测试期间先不要合盖，也不要退出 Docker 或关闭代理要求保留的服务。
5. 告诉代理你能提供的连续开始时间和结束时间，让它安排探测程序并记录时间。
6. 实际跑满 24 小时后，由代理分析原始结果；测试结束后可恢复原来的睡眠设置。

过程中断网、重启或维护，都如实告诉代理。你不需要一直盯着屏幕，但测试程序和被测服务需要持续运行。本机探测也不一定需要公网隧道；它能证明什么范围，由实际部署位置决定。
